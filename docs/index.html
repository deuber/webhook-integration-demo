Why webhooks?

The alternative to a webhook is polling: calling an API on a timer to ask "did anything change yet?" That means wasted calls when nothing happened, a real risk of hitting rate limits on a busy integration, and a built-in delay — you only find out about a change on your next poll, not the moment it occurs.

A webhook flips that from pull to push: the system that owns the data (GitHub, here) tells you the instant something happens, instead of you asking it over and over. You get near real-time delivery, no wasted requests, and no interval to tune between "too slow" and "burning through your rate limit."

The tradeoff is that a webhook handler has to earn that convenience: it has to prove a request really came from the sender (signature verification, below) and cope with a delivery model that isn't quite as tidy as a normal request/response call — namely retries and duplicates (dedupe, below).

How it works

GitHub fires an HTTP POST with a JSON payload to a URL you register the moment something happens — here, an issue being opened.

Signature verification: anyone can POST to a public URL, so every request carries an X-Hub-Signature-256 header — an HMAC of the raw body using a secret only you and GitHub know. The server recomputes it and rejects anything that doesn't match, using a constant-time comparison to avoid leaking timing information. (Below, this page computes that same HMAC for real in your browser via crypto.subtle — open the console panel to see it.)

Dedupe: webhook senders retry a delivery if they don't get a fast 2xx back, so the exact same event can legitimately arrive twice. Each delivery carries a unique X-GitHub-Delivery id — the handler remembers recently-seen ids and skips reprocessing a repeat instead of double-posting a comment.

Follow-up calls: once a new event is confirmed real, the handler makes a REST call to label and comment on the issue, and a GraphQL call to fetch the repo's open issue count — run concurrently, one API style for the write, the other for a targeted read.

With no GITHUB_TOKEN set — true for this static page, and true for the real server unless you provide one — those follow-up calls run in dry-run mode: logging the exact request instead of calling the real API.

How to confirm it's actually working

Not just "the page says so" — a few independent ways to check:

1. The HTTP response code. The real server returns 200 for anything it accepts (processed, ignored, or deduped) and 401 for a bad signature. When it's wired to a real GitHub repo, GitHub's own Settings → Webhooks → Recent Deliveries page shows every attempt with the exact request sent and response received — including a Redeliver button to resend a past delivery on demand. That page is the canonical, server-independent way to confirm and debug a webhook.

2. The real side effect. When run with a GITHUB_TOKEN, the label and comment the REST call posts show up on the actual GitHub issue — visible on github.com regardless of any dashboard, so they're proof the call really happened.

3. The server log and this page's console. The terminal running npm run dev shows each real delivery as it's received; this static page's console panel below shows the equivalent client-side trace for the simulation.

4. The CSV audit trail. The real server appends every processed and deduped event to data/processed-events.csv, so there's a record even after the process exits.

This static page can't produce most of that — there's no server, so no real GitHub webhook can target it. It's here to show the logic and the UI; the linked repo is where the italicized claims above become checkable.
